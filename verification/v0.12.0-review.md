# v0.12.0 I/O boundary review corrections

Date: 2026-10-02. Reviewed baseline: `5c7a1ed7e774b1e9043959e7943ca0feee4d5567`.
Corrected source: `412691b4c15601b1e8892e749ba4d2a1b6f628fa`.
The [initial implementation record](v0.12.0.md) remains evidence for its pinned
revision. The additional combinations below exposed gaps in that fixture set.

## Repeated stdin after invalid UTF-8

With a regular file containing 9,000 `A` bytes, byte FF, and 20,000 `B` bytes,
the first read fails decoding. At the reviewed baseline, the next read returned
16,713 bytes through `run` and 12,617 through native execution. The native read
request grew with staging capacity, consuming a larger prefix before failure.

Native reads now request at most 4,096 bytes, matching the host chunk size,
while staging still grows geometrically. Both backends now return exactly the
16,713-byte suffix. Additional cases move the invalid byte beyond later growth
boundaries and split an invalid scalar across a chunk boundary. Each backend
receives an independently opened regular file; pipe scheduling and independent
short reads are not assumed to have deterministic consumption boundaries.

## Startup diagnostic failure

Invalid runtime arguments now use a dedicated internal startup condition and a
best-effort diagnostic writer that preserves status 2. Compiler diagnostic
fallbacks retain their prior classification. The native startup writer already
preserved status 2.

The baseline host path could replace status 2 with 3 when reporting failed.
An actual CLI run with RLIMIT_FSIZE=1 also exposed buffered stderr retried after
signal restoration, terminating with SIGXFSZ. The startup writer now uses direct
fd writes and leaves no failed diagnostic buffered for process shutdown.
Both backends retain status 2 for the limited file, a readerless pipe, closed
stderr, and ENOSPC from `/dev/full`. Initializer and main side-effect markers
remain absent. Host write, flush, and storage failures also retain status 2.

## Test source failure and signal restoration

The driver now forwards the test runner's multiple return values, preserving
its primary-failure flag. A source error plus signal-restoration failure returned
3 at the baseline and now retains 1, with no test result or summary. Restoration
errors remain secondary. Tests restore the actual signal actions before
injecting the restoration report error, and verify action/fd state afterward.
Both the direct driver and the installed CLI's nested guard structure are
covered. Ordinary applications returning 1 or 2 remain non-primary outcomes;
a restoration failure still becomes an internal failure in those cases.
