# v0.9.0 development progress

Status: In progress
Updated: 2026-09-28

## Source and lexer increment

Development starts from the v0.8.1 implementation. This increment changes:

- Strict UTF-8 source rejects a leading BOM. U+FEFF inside string content is
  an ordinary scalar; it is not whitespace between tokens.
- Line comments start with `//` and end at CR, LF, or EOF. Source decoding
  still validates all bytes, including comments.
- The standalone underscore and decimal literals with leading zeroes are
  lexical errors. Underscores inside ordinary identifiers remain valid.
- Strings accept `\u{...}` with 1 to 6 ASCII hexadecimal digits denoting one
  Unicode scalar. Empty, oversized, surrogate, malformed, and unfinished
  escapes are rejected. Raw CR/LF remain errors; other scalar content is
  preserved without normalization.
- Source diagnostics carry zero-based, half-open UTF-8 byte ranges alongside
  one-based scalar line/column positions. Invalid continuation bytes identify
  the offending byte; truncated sequences identify the EOF boundary.
  The rendered form adds `[bytes start,end)`.

The lexer and source decoder are shared by the host and native build paths.
No new runtime representation or ABI is introduced by this increment.

## Evidence

Run from the repository root:

```sh
sbcl --noinform --script scripts/test.lisp
git diff --check
sha256sum -c verification/SHA256SUMS
```

The cumulative suite includes `tests/v09-source.lisp`. Its checks cover
comment boundaries and division, accepted/rejected escapes, non-normalized
Unicode equality, byte spans after multibyte characters, invalid UTF-8,
host/native execution, and preservation of an existing artifact on source
failure. Historical BOM and leading-zero tests are updated to the new
source rules. Older branch fixtures use explicit unused payload names instead
of the removed underscore pattern, retaining their original type/control/GC
checks. The exact tested revision and results are recorded in the PR.

## Remaining work

This completes an initial source/lexer increment, not the full frontend step.
The keyword/type-name migration, declaration headers and AST, forward name
classification, delimiter rules, grouped minimum-integer literal handling,
and complete legacy-syntax rejection remain.
Existing parser examples and the CLI retain their v0.8.1 spelling for now.

Subsequent increments still need isolated compile-time environments, type
graphs, completion analysis and its independent verifier, derivation-preserving
specialization, closure capture, lists and string results, Core/root handling,
native ABI/runtime changes, CLI/publication behavior, and integrated acceptance
and resource verification. No whole-language v0.9.0 conformance, main-branch
integration, or release is claimed.
