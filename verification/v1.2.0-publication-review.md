# Binary publication portability follow-up

This follow-up corrects a native filename assumption and changes environment
certification from an execution allowlist into evidence for error classification.
It supersedes the initial v1.2.0 restriction without changing released 1.x Int
or existing text/directory I/O behavior.

## Long final components

An absent name does not imply a name of at most 255 UTF-8 bytes. The former
native implementation copied a final component into a 256-byte stack buffer
and treated a larger absent name as an internal failure. The host did not
make that assumption.

Both adapters now check existing entries first, collect optional profile
evidence, and proceed independently of certification. Native code copies the
complete component and NUL into length-checked private Bytes storage rooted
through cleanup. It releases the original path mapping before staging.
The ownership proof checks the allocation bound and root installation.
Allocation failure follows the existing fatal allocation contract after cleanup;
it is not a filesystem error.

## Unverified environments

A missing certificate, unavailable probe, or unknown kernel/filesystem identity
does not reject a request. Publication still uses one direct
renameat2(RENAME_NOREPLACE), with no overwrite fallback and no commit retry.
Successful publication is Ok. Precommit failure is NotPublished. After a failed
commit, only an applicable proof permits NotPublished; otherwise the state is
Unknown. ENOSYS independently proves that the direct operation was unavailable.
Optional-probe descriptors are real owned resources: a close failure still
returns Cleanup/NotPublished.

UnsupportedTarget describes an observed unsupported operation or target, rather
than absence from the verification matrix. Certification never weakens target
protection. Unknown never triggers destination deletion or a retry.

## Evidence and reproduction

```sh
python3 tests/v120-publication-portability.py --evidence RESULT.json
python3 tests/v120-publication-portability.py --ntfs-root MOUNT --evidence NTFS.json
```

The optional fixture requires an already mounted, writable NTFS filesystem.
The harness does not format or mount it. Without that argument it explicitly
reports that NTFS was not requested.

A real ext4 checkout accepted both modes through host and native, preserving
raw bytes and expected permissions. A separately mounted ntfs-3g/FUSE fixture
accepted lookup of an absent 300-byte UTF-8 component. The original native
candidate exited through its internal-error path. The corrected host and native
both returned UnsupportedTarget/Publish/Unknown because an independent direct
RENAME_NOREPLACE probe returned EINVAL on that fixture. Existing long-name files
remain protected with AlreadyExists/Target/NotPublished. Neither case leaves
staging entries. These are ntfs-3g observations, not an execution claim for the
kernel ntfs3 driver.

The normal Lisp fixtures additionally inject a successful absent-name lookup
for a long component on a byte-limited filesystem. That synthetic observation
checks memory safety, error classification, GC stress and cleanup; it is not
evidence that the real filesystem accepts the component. Allocation-ordinal
fixtures cover all observed precommit and postcommit allocation failures.

Optional probe failures and identity mismatches are exercised in both backends
with successful commits and failed commits. The native tests use a small arena,
stress collection and heap validation. Full-suite results and exact candidate
identity are recorded in the integration pull request. Kernel-source evidence
for the existing certified profile remains in
[the profile record](v1.2.0-publication-profile.md); its C120-E06 structural N/A
does not certify every unverified environment.
