## Directory scratch mmap classification

At the reviewed baseline, injecting actual mmap ENOMEM or EINVAL during scan
buffer acquisition produced allocation-failed / exit 4 in both cases. The
shared file mapping helper consumed errno before directory phase classification.
The former private map-failure switch directly selected allocation-failed and
therefore did not establish EINVAL behavior.

Directory acquisition now calls a dedicated raw mmap adapter. The owning
operation classifies EINVAL as an internal inconsistency, latches the failure
and cleans known ownership records before the internal terminal. ENOMEM keeps
the existing allocation-failed path and primary-failure cleanup behavior.
Path, scan buffer, name arena and row-table growth all use this boundary.
The file helper retains its existing behavior. The private directory map fault
control now supplies a raw result before acquisition to the same classifier.

`v013-review-map-syscall-errors` uses strace syscall fault injection on the
production image. A successful baseline trace identifies every directory mmap
ordinal in a 100-entry long-name fixture; every ordinal is then tested with
ENOMEM and EINVAL. An independent trace oracle tracks each successful scratch
mapping by address and length, including old mappings during growth, and checks
unmap before the diagnostic and one close when a directory was opened.
createDirectory path acquisition and the older file allocation boundary have
separate controls. Injected failures do not create an unrecorded mapping.

`v013-review-map-runner-errors` uses the actual directory operation with a private
raw-result fault at scan allocation. In both initialization and body stages,
EINVAL yields child status 123, parent exit 3, one passed/one aborted/one not_run,
and no later test side effect. ENOMEM yields allocation-failed / parent exit 4
and allows the later test to run: two passed/one error. Attempts are reaped,
parent descriptors restored and temporary executable images removed.

## Internal-failure latch verification

At the reviewed baseline, independent mutations deleting or inverting the final
latch branch, or replacing its load with zero, were accepted by the Machine
verifier. Ownership traversal tracked records and descriptors without tracking
the latch or the register/condition facts used by its branch.

The verifier now interprets the emitted control flow with zero/nonzero latch
and register facts, comparison state and branch refinement. A latched failure
cannot be cleared or reach ordinary allocation, return or a language-failure
terminal. The existing frame, root and ownership checks remain active. The raw
mmap adapter must preserve its syscall result, and each production directory
map call must retain its phase-specific internal-error classification.

`v013-review-latch-flow-proofs` checks all three operations in normal and test
profiles. It rejects deletion, inversion, register clearing, latch clearing and
a jump around the decision. An equivalent zero-branch followed by an internal
jump is accepted, demonstrating control-flow reasoning beyond a gate template.
Mutations to the raw-map adapter, its call target and EINVAL decision are also
rejected. These checks are bounded Machine mutation evidence, not a proof
against arbitrary memory corruption.
