# Binary publication profile evidence

## Certified evidence profile

The initial certified evidence profile is `ubuntu-7.0.0-38-tmpfs`: Linux amd64,
release `7.0.0-38-generic`, version
`#38-Ubuntu SMP PREEMPT_DYNAMIC Fri Sep  4 09:10:14 UTC 2026`, and tmpfs.
This profile is evidence for failure classification, not an execution allowlist.
Other environments attempt the same no-replace operation. Success is accepted;
a failed commit without a no-publication proof is Unknown. Existing entries are
checked first and return AlreadyExists. This is not a certification of every
Linux filesystem or kernel.

The adapter verifies fstatfs type `0x01021994`, the statx `STATX_MNT_ID` return
mask and mount ID, and the matching mountinfo filesystem name. It reads
`/proc/self/mountinfo` in the calling namespace. Unavailable queries, identification failures and mismatches leave the operation
uncertified and do not reject publication. Failure to close a real probe
descriptor remains Cleanup/NotPublished. The native
parser streams bounded chunks without allocating a buffer for the whole file.
Mount quota, size, permission, read-only and execution restrictions remain OS
decisions. No mount condition bypasses the no-replace check.

## Commit-path argument

Both adapters issue one direct amd64 `renameat2` syscall, number 316, with the
same owned parent fd for both names and flags exactly `RENAME_NOREPLACE` (1).
They do not resend commit after EINTR or another error, and do not call ordinary
rename, destination unlink, copy, or a proxy service.

In `filename_renameat2`, name lookup, mount write access, locking, target
nonexistence, trailing-component checks and security checks precede
`vfs_rename`. Delegation and stale-lookup retries only follow a failure before
filesystem publication; the userspace adapter never retries a commit.

`vfs_rename` performs permission, policy, mountpoint and delegation checks before
calling the filesystem rename method. After a successful method call, its
dentry update and notification path cannot replace zero with a later errno.

For the admitted regular-file, same-parent, no-replace case, `shmem_rename2`
rejects unsupported flags and nonempty targets, then reserves a directory offset
with `simple_offset_add`. Allocation/offset exhaustion errors return before
namespace publication. The WHITEOUT and EXCHANGE branches are unreachable.
After successful reservation, offset transfer, link accounting and timestamp
updates return zero. `simple_offset_rename` is void; it cannot introduce a
post-publication error return. The final VFS dentry move establishes the visible
rename under the held rename locks.

Thus the certified profile's listed ordinary failures have no publication by this
call. This conclusion uses all exits of the admitted path, not one example
return site for each errno.

| Negative errno | Public kind |
|---|---|
| EEXIST, ENOTEMPTY | AlreadyExists |
| ENOENT | NotFound |
| EPERM, EACCES, EROFS | PermissionDenied |
| EXDEV, ENOTDIR, valid-flag EINVAL, ENOSYS, EOPNOTSUPP | UnsupportedTarget |
| ENOMEM, ENOSPC, EDQUOT | ResourceExhausted |
| EINTR, EAGAIN, EBUSY, ENAMETOOLONG, ELOOP, ESTALE | Other |

The latter row is also rejected before mutation on this admitted path.
ENOSYS independently means the direct syscall was unavailable. EIO is always
Unknown after commit is issued; unlisted errors or an invalid profile are also
Unknown. EBADF and EFAULT are internal failures, not public I/O errors.
Certifying another kernel revision requires a new source review and fixtures;
executing publication does not.

## Why ext4 is not certified

The inspected ext4 rename path can call `ext4_mark_inode_dirty` after adding the
new directory entry and then return its error. The present evidence does not
prove the required no-publication property for every ordinary resource-error
exit reachable through those helpers. Therefore ext4 has no registered
no-publication proof. Its successful operations still return Ok; failed commits
without independent proof return Unknown. A filesystem type magic shared by
ext2/ext3/ext4 is not accepted as certification evidence.

## Cleanup applicability

The file is closed before commit. The profile probe fd is closed before staging.
The native path mapping is released before staging after copying the final
component, including its NUL terminator, into checked, GC-rooted private Bytes
storage. ENOENT does not establish a 255-byte name limit. Allocation failure
before commit runs the owned-resource cleanup chain.
After commit, the only owned external resource is the parent O_PATH fd.
The host has no external path mapping to release.

For this exact kernel, `do_dentry_open` installs `empty_fops` for O_PATH.
`filp_flush` has no flush callback to invoke and returns zero for a valid owned
O_PATH descriptor; `close` then releases the descriptor. Neither adapter retries
close or exposes the owned fd. Double close and invalid pointers are internal
bugs. Host signal restoration belongs to the outer command guard, reports an
internal command failure, and cannot produce BinaryOutputError.

Consequently recoverable Cleanup/Published I/O failure is structurally
inapplicable to this implementation/profile. C120-E06 requires the ownership and
source review above. Synthetic post-close EIO tests are defensive state-machine
checks only; they are not evidence of a reachable kernel failure.

Result allocation follows resource cleanup. Its allocation failure preserves the
existing runtime-failure contract and is not an I/O cleanup error. Precommit
failures preserve the primary error while attempting owned-resource cleanup.
Cleanup compares the staging entry's device/inode with the owned file before
unlinking it. Unknown never causes a destination lookup, removal or retry.

## Executable evidence

`tests/v120-publication.lisp` injects raw syscall observations before operations
and after real close, separately checks short actual writes, and models a lost
reply after a real successful commit. It checks error kind, original subject,
phase, publication state and output retention in both backends.

`tests/v120-publication.py` observes raw octets, empty output, all byte values,
umask and default ACL results, setgid-parent behavior, existing entry kinds,
trailing slash rejection, intermediate symlinks, unverified-filesystem execution, real
RLIMIT_FSIZE failure, concurrent publishers and absence of staging leftovers.
Synthetic failures supplement the source proof; they do not replace it.

The [portability review](v1.2.0-publication-review.md) records the policy change,
long-component regression and actual filesystem observations.
